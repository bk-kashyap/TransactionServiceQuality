# C1: Strategy, risk and metrics

The objective is correct and traceable financial effects, not maximizing tests. The published contract is a provider claim. Mock passes cannot retire real-service risk. P0 means direct financial loss, unauthorized effects or systemic integrity failure; P1 serious recoverability/operability impact; P2 degraded service without incorrect money movement. Likelihood is initial judgment, not measured telemetry.

| ID | Failure | Priority | Business rationale |
|---|---|---|---|
| R-01 | Double debit/replay race | P0 | Customer charged twice; retries amplify exposure |
| R-02 | Wrong debit/credit direction | P0 | Purchase credits or voucher debits customer |
| R-03 | Amount/unit/precision corruption | P0 | Money value changes in storage or caller-unit round-trip |
| R-04 | Wrong/nonexistent account association | P0 | Effect belongs to the wrong person |
| R-05 | Accepted but lost/inconsistent record | P0 | Ledger and API cannot reconcile |
| R-06 | Invalid/duplicate account | P1 | Identity integrity; uniqueness requires agreement |
| R-07 | Invalid inputs accepted | P1 | Corrupt records or uncontrolled failures |
| R-08 | Missing audit/tracing | P1; P0 for mandatory audit loss | Cannot reconstruct money effects/recover incidents |
| R-09 | Contract/HTTP incompatibility | P1/P2 | Consumers cannot safely interpret responses |
| R-10 | Exhaustion/latency | P2; P0 if retries double-charge | Availability cost depends on financial effects |
| R-11 | Unauthorized account access | P0 | Unauthorized disclosure or money movement |

## Pyramid and ownership

Developer unit/component tests own arithmetic, enum mapping, validation, uniqueness, rollback and atomic idempotency. QA independently challenges API outcomes, contracts, consumer compatibility, concurrent replay and a small account-to-transaction journey. Dev/QA/Product/Security/Ops jointly agree oracles and release acceptance; QA recommends risk decisions rather than inventing financial requirements.

Contract tests cheaply catch malformed schemas, references, wrong present-property types and response/status drift. They cannot enforce absent rules. Functional tests exercise boundaries/identity/money/replay under agreed policy. E2E covers all four operations and resulting records through a read adapter without repeating every permutation. Real integration/fault tests must establish persistence/atomicity.

Deliberately excluded: hidden DB layout, speculative installment/refund rules, unexposed balances, and browser UI. Missing capabilities remain findings. The local two-decimal money policy is a synthetic assumption.

## Release dashboard design (no production values measured)

| Signal | Definition/source/window | Initial threshold | Owner/action |
|---|---|---|---|
| Duplicate effects | Authoritative postings grouped by tenant/account/key, rolling 1 min | Any group count >1 | Page Payments Ops and transaction on-call |
| Reconciliation mismatch | Ledger/posting differences, rolling 5 min | Any unexplained mismatch | Stop rollout; Finance/Ops investigate |
| Release blockers | Open P0s plus missing required oracles, tracker/evidence manifest | Zero | Release manager denies sign-off otherwise |
| Verified critical risks | Required risks with passing real evidence / required risks | 100%, BLOCKED distinct from FAILED | QA publishes observations/owners |
| Technical error rate | 5xx/transport errors / attempts, telemetry, rolling 5 min | Assumption <1% | On-call correlates retries/duplicates |
| Latency/throughput | p95/p99 and completed arrivals by operation, telemetry/load tool | Assumed 100 TPS, p95 <500 ms, p99 <1 s | Platform/provider confirm targets |
| Feedback reliability | First-attempt failures by product/environment/test/unknown, CI | No hidden retry passes | QA/dev investigate before changing gates |

Sketch: `Release blockers | verified financial risks | duplicate effects | reconciliation | latency/error trends | evidence environment`. Values are initially UNMEASURED/BLOCKED. Pass rate, count and coverage percentage describe the portfolio; they do not establish financial safety.

## Blocking questions

Blocking: scoped idempotency/TTL/replay/conflict; authoritative count/read and consistency; currency/caller/storage units and rounding/limits; security principals/ownership; audit atomicity evidence. Establish whether the service owns balances or only records operations before requiring balance invariants. Document uniqueness blocks only if agreed onboarding requires it. Request-ID naming, lifecycle/history, cleanup and consumer interfaces need owners; priority follows scope.

Production position: NO-GO. The reference suite proves a synthetic harness, and Prism proves schema interpretation. Neither proves the provider correct.
