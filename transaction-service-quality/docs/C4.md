# STEP 1 — First understand what the contract actually promises

This is where your C4 can become Staff-level rather than simply "many test cases."

## 1.1 Account contract

The request contains:

```json
{
  "document_number": "12345678900"
}
```

The contract says `document_number` is a string, but it gives **no minLength, maxLength, pattern, uniqueness constraint, or required property constraint**. 

That creates several important gaps.

| Requirement               | Contract says                            | Hearsay             | Our test              |
| ------------------------- | ---------------------------------------- | ------------------- | --------------------- |
| document number is string | Yes                                      | —                   | Yes                   |
| 10–14 digits              | No                                       | Yes                 | Yes, but mark hearsay |
| minimum length            | No                                       | "something like 10" | Boundary test         |
| maximum length            | No                                       | "something like 14" | Boundary test         |
| only digits               | No                                       | implied             | Test                  |
| duplicate document number | No                                       | not stated          | Test / open question  |
| empty string              | No                                       | —                   | Test                  |
| null                      | No                                       | —                   | Test                  |
| missing field             | Body required, field itself not required | —                   | Test                  |

**This distinction is critical.**

Do not write:

> "The API must reject document numbers shorter than 10 digits."

Write:

> "Expected rejection — authority: hearsay. The published contract does not define the boundary, therefore this test currently represents an implementation expectation requiring confirmation."

That demonstrates exactly the judgment the assignment is looking for.

# STEP 2 — Transaction contract

The transaction request is:


The schema defines all three as integer/number/integer.

> Operation type IDs: 1=Normal Purchase, 2=Purchase with installments, 3=Withdrawal, 4=Credit Voucher.

and:

> Send a positive amount. The server applies the correct sign based on operation type.



So these are **contract-backed**:

| Operation                  | ID |    Input | Expected sign               |
| -------------------------- | -: | -------: | --------------------------- |
| Normal Purchase            |  1 | positive | Server applies correct sign |
| Purchase with installments |  2 | positive | Server applies correct sign |
| Withdrawal                 |  3 | positive | Server applies correct sign |
| Credit Voucher             |  4 | positive | Server applies correct sign |

But the contract does **not explicitly say**:

```text

2 -> negative
3 -> negative
4 -> positive
```

That comes from the assignment's hearsay:

> Purchases and withdrawals go negative, credit vouchers go positive.

Therefore:

**sign expectation = hearsay/domain expectation, not contract guarantee.**

That is exactly the distinction you should show.

# STEP 4 — The most important C4 insight: round-trip amount

The assignment specifically asks for:

> amount round tripping back to the caller's unit.

The standup hearsay says:

> amounts go in as rupees, we store them in the smallest unit internally.

That is **not in the OpenAPI contract**.

So our test should be:

```text
Input:
50.25 INR

Expected:
response.amount = -50.25
```

for a debit operation.

But classify the authority as:

```text
HEARSAY + DOMAIN REASONING
```

not contract.

This gives you a very strong C4 observation:

> The API contract needs to specify monetary precision and representation. A `number` alone is insufficient to establish currency, scale, rounding behaviour or smallest-unit conversion semantics.

That's a potential **C3/C5 finding**, not merely a test case.

But there's a subtle issue here.

### Don't use JavaScript floating-point equality blindly.

For money:

```typescript
expect(response.amount).toBe(-10.01);
```

can become dangerous because JavaScript uses IEEE-754 floating-point numbers.

For financial assertions, preferably compare using a decimal representation.

For example:

```typescript
expect(response.amount.toString()).toBe('-10.01');
```

or use a decimal library such as `decimal.js` if the API precision requirements justify it.

This is exactly the type of quality thinking the assignment is looking for.

# STEP 11 — Idempotency

This is one of your biggest C4/C5 areas.

The assignment's hearsay says there is an idempotency header:

```text
same key → original response
```

But look carefully at the supplied YAML.

There is **no idempotency header defined** anywhere.

Therefore:

| Case                              | Authority                               |
| --------------------------------- | --------------------------------------- |
| Same key replay                   | HEARSAY                                 |
| Same key + different body         | DOMAIN / HEARSAY                        |
| Missing key                       | CONTRACT GAP                            |
| Header name                       | CONTRACT GAP                            |
| Response behaviour                | CONTRACT GAP                            |
| Exactly one transaction persisted | NOT OBSERVABLE through current contract |

That last point is extremely important because T1 asks you to prove exactly one transaction was created.

The assignment itself says the published API may not allow you to verify that. 

### Your C4 tests should still exist.

Example:

```text
IDEMP-001
POST transaction with key K1

IDEMP-002
Replay exact request with K1

IDEMP-003
K1 + different amount

IDEMP-004
K1 + different account

IDEMP-005
No idempotency key
```

But mark them:

```text
Status = BLOCKED / CONTRACT GAP
```

where appropriate rather than inventing expected HTTP responses.
