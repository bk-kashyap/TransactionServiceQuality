C3 — Contract Audit & Schema-Driven Validation : 

The contract does document the four transaction operation types and the sign behavior, which gives us a useful starting point for automated validation.

I would therefore classify the findings into four categories:
| Classification                   | Meaning                                                | Priority      |

| C1 — Contract correctness        | The API cannot reliably validate what the schema claims | **Critical/High** |
| C2 — Payment-domain completeness | Important card/payment behavior is absent from the contract | **High**        |
| C3 — Consumer safety      | Mobile/ledger consumers cannot safely depend on the contract | **High**        |
| C4 — Operability/security | Production concerns such as auth, idempotency and observability are unspecified| **High** |


This is useful because it distinguishes "the schema is technically weak" from "the payment product itself is underspecified."

1. Contract Audit Findings Register : 

     Request fields are not mandatory. Why?
     Missing required constraints

     The account creation request contains only <document_number>, but the property is not marked <required>.

     The transaction request similarly contains:
          account_id
          amount
          operation_type_id

     but none is declared required.

     Risk is : The following could potentially pass schema validation :
     JSON : 
          {}
     OR 
     JSON :
     {
          "account_id": 1
     }

     Note : For a financial API this is unacceptable.

     Solution and open for discussion :
     Recommendation : 
          Define:

          required:
               - account_id
               - amount
               - operation_type_id

          and:

          required:
               - document_number

2. No validation for amount : 
     There is no minimum, maximum, precision or format constraint.

     Missing rules

     At minimum, the contract should clarify:

        -   Can amount be 0?
        -   Can amount be negative?
        -   Maximum transaction amount?
        -   Decimal precision?
        -   Currency?
        -   Number of decimal places?
        -   Is scientific notation accepted?
        -   Maximum number of digits?

     For financial transactions, number alone is insufficient.

     Boundary-value tests: 

          | Input             | Expected                |
          | ----------------- | ----------------------- |
          | `0`               | Reject                  |
          | `-1`              | Reject                  |
          | `0.01`            | Accept                  |
          | `1.999`           | Reject/defined behavior |
          | Maximum allowed   | Accept                  |
          | Maximum + 0.01    | Reject                  |
          | Very large number | Reject                  |

3. <operation_type_id> is an unrestricted integer : 
     The contract describes:
          1=Normal Purchase, 
          2=Purchase with installments, 
          3=Withdrawal, 
          4=Credit Voucher.

     But the schema only says:

          operation_type_id:
               - type: integer

     Problem : There is no schema-level restriction preventing:
          {
          "operation_type_id": 999
          }

     Recommendation : Use an enum if the IDs are truly fixed:

          operation_type_id:
               type: integer
               enum: [1, 2, 3, 4]

     Automation : Create a data-driven test:
          1 → valid
          2 → valid
          3 → valid
          4 → valid
          0 → invalid
          5 → invalid
          999 → invalid
          null → invalid

     | Installment Purchase | Debit       | Negative |
     | Withdrawal           | Debit       | Negative |
     | Credit Voucher       | Credit      | Positive |

     a. Response type is unrestricted : 
          Recommendation : 
               If the valid values are debit and credit:

               type:
               type: string
               enum:
               - debit

          -   length
          -   numeric-only constraint
          -   regex
          -   document type
          -   checksum
          -   masking requirements
          -   uniqueness
          -   duplicate-account behavior

     Important QA position : Do not automatically decide that 11 digits is the correct rule simply because the example contains 11 digits. The contract needs the business rule first.

          Automation : 
          Once confirmed:
               -   null
               -   empty
               -   too short
               -   too long
               -   alphabetic
               -   special characters
               -   duplicate
               -   valid document

5. Account identifier constraints are weak. <account_id>

     <account_id> is simply an integer in both request and response.
     Missing:      
          -   minimum value
          -   whether zero is valid
          -   maximum value
          -   account lifecycle/status
          -   whether deleted/blocked accounts can transact

     Critical transaction rule : The transaction description explicitly says the transaction is against an existing account. Therefore this should be explicitly tested:

          Unknown account
          → 422 or defined business error.
          The contract already defines 422 for /transactions.

6. Error model is too weak : 
     The entire error contract is:
          error:
               type: string

     This makes automation and consumer behavior unnecessarily fragile.
     A better error contract would contain something like:

     {
     "code": "ACCOUNT_NOT_FOUND",
     "message": "Account does not exist",
     "details": []
     }
     So, the complete error model needs a major discussion with PO.

7. No authentication/security contract.
     The API exposed to public, that's castroscopic : 
          /accounts
          /accounts/{accountId}
          /transactions

     But the supplied contract does not specify authentication/security schemes.
     For a cardholder/payment service, the contract should define at least the expected security mechanism, for example:

          -   OAuth2 / JWT
          -   API authorization scopes
          -   service-to-service authentication

          The exact mechanism should be confirmed by architecture/security.
          Tests & Automate:
               -   No token → 401
               -   Invalid token → 401
               -   Expired token → 401
               -   Insufficient scope → 403
               -   Valid token → success

8. No idempotency contract.
9. No concurrency/duplicate transaction behavior.
     Questions needing specification:

          -   Are both accepted?
          -   Is one rejected?
          -   Is there account-level locking?
          -   How is balance consistency maintained?
          -   What is the ordering authority?

     This is particularly important for a ledger consumer.

10. No currency : 
     For a production payment API, this needs clarification:

          -   currency = INR?
          -   currency = USD?
          -   multi-currency?
          -   account determines currency?

     If the account has a fixed currency, the contract should document that relationship.

11. No transaction lifecycle/status : 

     The current transaction response contains:

          -   account ID
          -   amount
          -   event date
          -   operation type
          -   transaction ID
          -   type

     But there is no explicit transaction status such as:

          -   PENDING
          -   POSTED
          -   FAILED
          -   REVERSED
          -   CANCELLED

     Whether this is required depends on the service architecture (it's an explicit architectural decision).

12. No transaction retrieval API : 
     The contract creates transactions but provides no API for it's retrieval.
          GET /transactions/{transactionId}
     And no transaction history API
          GET /accounts/{accountId}/transactions

13. No pagination/filtering/sorting for transaction history
     Related to the above, if transaction retrieval is eventually required, the contract needs:

          -   page
          -   pageSize
          -   fromDate
          -   toDate
          -   type
          -   status
          -   sort

     Again, mark this as **pending requirement**, not automatically as a contract defect.

21. Request/response schema validation : 

     Every automated API test should validate both:
          HTTP behavior
          +
          schema compliance

     For example:
          POST /transactions
               │
               ├── HTTP status = 201
               │
               ├── Content-Type = application/json
               │
               ├── response matches transactionResponse
               │
               └── business assertions

     This prevents a common QA problem:
          "The API returned 201, therefore the test passed."
          A 201 response containing the wrong JSON should fail.

25. Most important conclusions for the interviewer

If you need to explain C3 verbally, I would make these five points:

1. The current YAML is structurally valid as a basic Swagger contract, but it is under-specified for a financial transaction service.

2. My biggest contract gaps are mandatory fields, amount constraints, operation-type enumeration, error semantics, authentication, idempotency, currency, and financial transaction invariants.

3. I would not make QA invent missing business rules. I would explicitly classify them as pending requirements and write executable tests once the business authority defines them.

4. I would use the OpenAPI contract as the schema authority, Playwright for executable API/contract validation, and Pact for consumer-driven contracts between the transaction service and mobile/ledger consumers.

5. I would generate the mock from the same contract and run the same suite against mock and staging, supplemented with scheduled provider/contract checks to detect mock and production drift.
